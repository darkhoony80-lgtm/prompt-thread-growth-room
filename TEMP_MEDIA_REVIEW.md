# Temporary publication media

Draft creation, file selection, archive import, merged video encoding and AI/webtoon generation now keep media in the origin's IndexedDB. They do not upload to Blob. Existing PC folders and archive files are not modified or deleted. IndexedDB is a browser cache: clearing browser data, changing browser/profile/origin or eviction can remove it. Keep PC originals and use the existing archive export before relying on recovery. No backup completeness has been established.

Publication uploads only the media selected by each platform adapter. Files are hashed by bytes and successful upload receipts persist with the local file. Repeated publication retries and simultaneous tabs use the same receipt (Web Locks serialize uploads on supported browsers). Each new upload gets a server-issued signed intent for `content-master/temp-<server UUID>/<SHA-256>.<extension>`; Vercel may add a random suffix. Legacy HTTPS references are preserved and excluded from the new cleanup ledger.

The existing Instagram publication route still receives public Blob URLs and the same `request_id`, `content_id`, `content_type` and `reply_prompt`; the Supabase prompt upsert and automatic reply handlers are unchanged. Individual webtoon cuts stay local and are sent as JPEG data for composition; only final images selected for publication upload. Composition request data is limited to 4 MB and remains subject to Vercel's platform payload limit.

## Recover an interrupted upload

A failed or interrupted upload may have created a remote file without returning a receipt. It stays `pending` and blocks blind duplicate retries. Download **임시 미디어 검토 목록** from the top bar. Use the authenticated Vercel store file list to check that exact temporary path and size. Only after that check, use `LocalMedia.reconcile(id, exactRemoteUrl)` to recover its receipt, or `LocalMedia.reconcile(id, null)` if the inventory proves no corresponding file exists. Both require a user confirmation. This changes only the local receipt. Do not guess a URL or clear pending records blindly. No inventory access means recovery remains blocked.

## Automatic cleanup policy (implemented, inactive until configured)

This release hard-disables deletion with `TEMP_MEDIA_CLEANUP_RELEASE_ENABLED=false`, including when `TEMP_MEDIA_AUTO_CLEANUP=1` is configured. `GET /api/content-router?action=temp_media_policy` reports the non-secret release/environment/effective flags without accessing Blob or Meta. No deployed setting has been changed. After the quota restriction lifts, perform separately approved integration validation before changing the release gate and configuring `TEMP_MEDIA_AUTO_CLEANUP=1`. `TEMP_MEDIA_RETENTION_HOURS` defaults to 24 and must be between 24 and 8760. The hold is an operational assumption, not a Meta guarantee that the source can be deleted. Real post/media accessibility after source removal has NOT been tested. Explain and approve that policy before activation.

While the app is open, the scheduler checks at startup and every five minutes. It resumes persisted work when the same browser/profile/origin is reopened; it does not run with the browser closed. An eligible file needs its signed upload intent, matching exact Blob URL/path/size, completed local publication receipt, no active job references and a fresh server check of every recorded Threads/Instagram post. The check requires a published permalink and final media URLs on known Meta CDN hosts; missing/unsupported fields, missing sessions/tokens, API errors or source URLs still pointing at Blob block cleanup. Metadata and platform evidence are checked again immediately before deletion. Delays start at server verification, not at an untrusted client timestamp.

Only this server-issued unique temporary namespace is accepted. Existing admin authentication and same-origin checks protect all three intent/completion/cleanup routes. Canonical public Blob host, exact signed path including only a permitted random suffix, object metadata and HMAC purpose/type are validated before deletion. Supplied arbitrary URLs, legacy/shared paths, traversal and forged receipts cannot become deletion targets. There is no user-supplied fetch destination for the Meta verification calls.

Web Locks cover preparation, upload and cleanup for each file within an origin. Active jobs are written to IndexedDB before upload, and only the matching job's successful publication releases its reference. Tabs get separate identities even for the same content/job ID. Failed or ambiguous jobs retain their references; they do not expire automatically. External/manual sharing of an owned temporary URL across other browsers/origins is not tracked: do not enable this policy for externally shared source URLs. Draft previews and queued work use local cache bytes and can upload a fresh temporary file after cleanup. Facebook/YouTube publication receipts are retained, not auto-deleted, because their final-source verification is not implemented.

Deletion attempts, errors, retry count and next attempt time persist in IndexedDB. Failures back off up to one hour; already-absent objects after an interrupted delete are idempotent successes. Cleanup clears the remote receipt and retains cache bytes and historical preview aliases so later use creates a new signed upload. It does not remove PC files, drafts, published history, Supabase rows or configuration. Clearing/evicting the browser cache can lose the ledger; then that origin's leftovers cannot be automatically discovered or deleted.

## Manual review / recovery of blocked entries

A response lost after publication can leave a live job without a receipt: verify actual platform publication before resending. Review ambiguous and failed work rather than expiring references. The review export includes active job IDs, cleanup states, retry counts and errors. Unknown external references and unavailable backups require manual review.

1. Download the review JSON on the same browser/profile/origin. Compare every owned path and exact URL against the authenticated store inventory. Include pending and failed uploads in investigation, not automatic deletion.
2. Verify completed platform posts and their accessible images/videos. Obtain evidence that the source is no longer required; no arbitrary elapsed time is a guarantee.
3. Check all production/custom-domain/preview origins, other browsers and local archive manifests for ongoing drafts, scheduled jobs and other consumers of the same URL. One hash can serve multiple jobs/platforms. The ledger alone does not prove absence of other references.
4. Verify readable PC backups with matching bytes/hash. `local_original_present` in the JSON means IndexedDB only, not a verified PC backup.
5. For manual cleanup of blocked files, present exact URLs, sizes, safety evidence and total reclaimable bytes for explicit user approval. Delete only those approved files via the authenticated store UI or supported tool. Do not delete the store, project, Supabase rows or legacy prefixes as part of this procedure.
6. Verify selected URLs are removed and reconcile receipts before reusing those media. Until reconciliation, a receipt may point at a deleted file. Existing disk originals and browser cache remain unchanged.

Verified Threads/Instagram temporary files are automatically removed under the activated policy. Failed, uncertain, externally shared, unsupported-platform or lost-ledger files can remain; there is no unconditional zero-growth promise.

## Validation and remaining limits

`node --test tests/*.test.cjs` exercises existing auto-post/recovery behavior and the new lifecycle with mocked storage/Blob SDK and Meta: no draft upload, byte preservation, content reuse, concurrent references, reload recovery, ambiguous interruption, Instagram mapping fields, auth/origin checks, signed ownership, SSRF/path rejection, retention, fresh publication checks, idempotent deletion, retry persistence and preservation of local bytes. No test performs an actual social publication or remote deletion. Parent-side deletion of old store files was completed separately; remaining quota suspension blocks real upload integration. Deployment, push and real activation are outside this change.

An isolated headless Chrome loaded the real local app with all API calls mocked. A valid 767-byte JPEG was added through `PostAuto.addMedia`, previewed at 32×32, and recovered after reload using the real IndexedDB adapter and a new working object URL. File selection and mocked PC archive import both produced zero upload/intent requests and no alerts/page errors. This is local cache/UI verification, not a test of actual PC backups, Blob, Meta or automatic source deletion after publication.
